# Milestone 3 Sol review findings — implementation in progress

These are independent review observations before any M3 development migration is applied. Opus implementation is still running; this document is not a completed acceptance result.

1. **P1 — changing work after resolution leaves stale evidence eligible for verification.** The first draft of private.update_action accepts ready_for_verification and lets the reviewer change issue, action_required, severity or assignee while keeping the old resolution evidence/resolver/readiness. For example, resolve cleaning, then change the required work to repairing equipment, then verify without evidence of the new work. Require an explicit return-for-work (reasoned, clearing current resolution) before substantive edits/reassignment, or atomically return to in_progress with a reason and preserve the old evidence in immutable history. A due-date-only change can remain ready. Add a SQL regression proving prior evidence cannot close changed work, and make the UI explain the return step.
2. **P2 — due-today notification remains live after its day ends.** private.render_notification checks status and matching due date, but does not compare the current workspace-local date with notification kind. The old action_due_today entry continues saying Due today when it is actually overdue; the new overdue notification also counts. Recheck kind against the shared due_state/workspace_today function. An old due-today reminder must become stale after midnight; an overdue reminder becomes stale when no longer overdue. Test with fixed due-state parameters and real SQL dates.
3. **P2 — manual finding create replay returns mutable version.** private.create_finding returns v_prior.version on retry, so withdrawal changes a create receipt from v1 to v2. Return the original create receipt version (1), with replay flag, under the live permission check. Demonstrate retry after withdrawal gives the original receipt and no new event.

Further review of reports, analysis, triggers, exports and UI follows when those drafts exist. Applied migrations and the 15 baseline snapshots remain unchanged.
4. **P1 — repeat source references need live scope checks.** The generated finding detail embeds prior_sessions and sessions_with_finding across locations in the workspace. redact_inputs currently passes findings unchanged, so a location-scoped Viewer/Reviewer receiving an authorized current report could learn IDs of prior inspections outside their report scope. Filter source references through the caller's live report access in report and analysis read envelopes, without changing stored snapshots. Mark restricted sources as withheld rather than falsifying the frozen repeat result. No raw out-of-scope source IDs in UI/CSV/PDF payloads. Add a two-location test where a repeated critical finding references an inspection the current reader cannot access.

## Independent reproductions

Before fixes, tests/sql/sol-action-invariants.test.ts reproduces all four issues on empty-replayed local Postgres: substantive ready-action changes retain old evidence; yesterday's due-today notification remains live; finding-create replay changes to version2 after withdrawal; real generated repeat evidence reveals an inaccessible prior location's session ID to a scoped Viewer. These are failing acceptance regressions, not hypothetical warnings. Opus must repair them without weakening assertions.

The separate tests/sql/sol-legacy-m3.test.ts passes both independent regressions: a deterministic M2 waiver/absence/removed-evidence fixture redacts byte-identically after M3; all 15 saved disposable approvals (7 M1,8 M2) retain their body hashes and exact pre-M3 redacted outputs. Full exit testing still remains.

Scope repair must cover **every** read surface: get_session_report, get_analytics (record inputs and live finding repeat data), get_findings, get_action's linked finding, and authenticated direct SELECT of findings.detail. Assignees are allowed their linked finding but not unrelated inspection IDs embedded in its detail. If raw finding detail cannot be redacted through table RLS, use appropriate column privileges or RPC-only detail reads; retain legitimate row visibility checks without exposing raw detail. Filter referenced inspection IDs by live can_review or viewer_can_see, not mere workspace membership. Historical stored bodies must remain byte-identical; scrub only outgoing envelopes, with a truthful restricted-source disclosure.
5. **P2 — unknown outcomes hide missing/waived work in analysis counts.** analytics.counts sums missing/waived responses only for status=incomplete. In provisional data, an unknown subject can have required=2, responses=0, waived=1 and therefore display unknown1 but missing0/waived0. Disclose actual outstanding quality work and waivers even if outcome remains unknown; exclude true absence/not-assessed/attendance-only obligations appropriately and explain denominators. The independent fixture expects missing2/waived1 for unknown required quality work, with null quality.
6. **P2 — subject-level live flag filtering can attach the wrong source/category or omit selected new work.** buildAnalytics checks only whether a subject ID appears anywhere in filtered approved rows. A subject in category A in one inspection and B in another can leak B's overdue action into category A's comparison. Conversely an explicit subject filter suppresses that subject's overdue work before its first approval. Apply filters to each source's session/subject and truthful historical/live category/type context, not a global subject-ID union. Explicit subject-ID selection must work for live operations without approved history. Label live sources separately from approved metrics. Independent tests in sol-analytics-m3.test.ts reproduce both cases.
7. **P2 — current action appendix export detail differs between formats.** The PDF currently renders current action status/issue/due/assignee/update time but omits its resolution evidence, while CSV includes evidence; neither current section includes the required work or verified-at/cancel reason fields already returned by the RPC. A report approved while an action was Open can later show Closed with no explanation in PDF. Use a shared action presentation definition across UI/CSV/PDF so required work, evidence, verification time and cancellation reason (when present) are retained in the dated current appendix, including redacted mode. The frozen section must remain explicitly tied to its revision. Exercise text/metadata privacy and render a real PDF with post-approval closure evidence.

Release packaging check: analytics PDF uses the embedded fonts too; next.config outputFileTracingIncludes must cover the new analytics export route as well as the session report route. Verify the hosted download, not only a local build.
8. **P1 — action URL/form business context is not checked against the entity.** ActionPage requires membership in route workspace A, then calls get_action(id) without verifying the returned action belongs to A. A user who belongs to A and B can open /w/A/actions/<B-action> and see/edit B's action under A's business header. The mutation wrappers use requireUser only and treat posted ws as a cache path; they never assert action/finding/session workspace equals that ws. Preserve entity-level SQL authorization, but also enforce route/form business context, including for users legitimately active in both businesses. Return workspace_id in action data (or another authorized lookup), reject mismatched action/detail, finding/session writes and notification marking before mutation. Assignees must still avoid full session access. Add an independent multi-membership regression for wrong-workspace URLs/forms; a single-membership cross-tenant denial test does not catch this.
