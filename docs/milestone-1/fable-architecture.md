# SAVOUR SaaS Milestone 1 architecture

**Repo layout.** Everything new lives under `saas/`: a Next.js App Router app, a pure TypeScript scoring package, and a Supabase folder with versioned migrations, seed data and database tests. Root legacy HTML and Firebase files stay untouched. The dev project ilhutasrxnbtssswmgam and the savour-dev Vercel preview are the only targets. The app runtime holds only the anon key and project URL. The service role key never appears in app code or Vercel env.

## Schema, RPC boundaries and RLS

**Minimum tables.** All tenant tables carry an immutable workspace key, enforced by a before-update trigger that rejects any change to it. Child tables use composite foreign keys that include the workspace key, so a session cannot reference a roster subject from another tenant.

- Identity: profiles, workspaces, memberships with role, status, revoked_at and a display-name snapshot, membership_locations, invites with lowercase email, token hash, role, location list, expiry, revoked_at and accepted_at. Membership is unique per workspace and user. A check trigger forbids removing or demoting the last active owner.
- Setup: locations, categories, subjects with workspace-local key, type, display name, archived_at, subject_locations, templates and template_versions. A published version stores its criteria, attendance mode, N/A permissions and formula version as immutable content. Publishing is insert-only.
- Evidence: sessions with opaque id, location, local date, status, reviewer membership, template version, open and close instants, expected ready time and an integer version column. session_subjects as the roster, holding the canonical outcome, final attendance, reason, resolver and version. session_assignments linking a member or guest grant to a session and permitted subjects. assessments keyed uniquely by session, subject and assessor with a pointer to the current revision. assessment_revisions holding scores, observed attendance, N/A reasons, observations and an idempotency key unique per assessor.
- Review: report_revisions with revision number, status pending or approved, frozen inputs, approver user id, approver name snapshot, approval instant, calculation version, reopen reason and an is_current flag. audit_events as an insert-only log written by RPCs. guest_grants binding an authenticated user to one session, permitted subjects and an expiry.

**Write boundary.** The authenticated role gets SELECT only, under RLS. It gets no INSERT, UPDATE or DELETE on any table. Every mutation is a named Postgres function: create_workspace, create_invite, revoke_invite, accept_invite, revoke_membership, publish_template_version, create_session, open_session, close_collection, amend_roster, assign_assessor, submit_assessment, resolve_subject_outcome, request_correction, amend_assessment, approve_session, reopen_session, cancel_session, record_export. Each function is SECURITY DEFINER with a fixed search path, EXECUTE revoked from public and anon, and begins by resolving auth.uid() to an active membership with the required role and location scope. Each takes an expected version where applicable and raises a distinct conflict error on mismatch, mapped to HTTP 409 by the server. Each writes its audit event in the same transaction. This is constrained logic inside the database, not a privileged client bypass. Revocation takes effect on the next request because every function and policy reads membership status live rather than trusting token claims.

**RLS without recursion.** Policies never query memberships through a policy-protected path. A small set of STABLE SECURITY DEFINER helpers, owned by the migration owner so RLS does not apply inside them, answer three questions: is this user an active member of this workspace with one of these roles, does this user hold this location, and does this user hold a live guest grant for this session. Every policy calls only these helpers plus auth.uid(). The memberships table itself has one self-read policy on user id and one owner-or-admin read policy via the helper. Guest grants grant read of exactly one session, its roster subjects and the guest's own assessments. Assessors cannot select peer assessments until the current report revision is approved. Viewers select approved revisions only.

**Invitation acceptance.** The link carries a random token. Only its hash is stored. The accept page requires sign-in first through Supabase email OTP or magic link. The accept function locks the invite row, requires a verified caller email equal to the stored lowercase email, matches the hash, rejects expired, revoked or already accepted invites, and creates the membership using the role and locations from the invite row only. Caller-supplied role is never read. Invites can never carry the owner role. Ownership transfer is deferred.

## Calculations, auth, exports

**Canonical attendance and scoring.** Assessors record observed attendance in their revisions. The reviewer sets one final outcome per subject-session through resolve_subject_outcome with a version check. Absence stores attendance points 0 and forces quality to null for that subject-session. With attendance Off the outcome is Assessed or Not assessed with reason. Approval refuses while any roster outcome is Unknown or any required assignment is unresolved and unwaived.

**Transactions versus server JS.** The database owns facts and transitions. The scoring package owns arithmetic. approve_session runs one transaction: lock the session, check status In review and version, check every outcome and assignment, then copy the exact inputs into the report revision. Inputs are the template version content, the roster outcomes and the current revision of every assessment, with a content hash. It then stamps approver id, name snapshot, server time and calculation version. The scoring package computes quality, combined, subject-session mean and coverage deterministically from those frozen inputs, keyed by calculation version. Dashboard, CSV and PDF all call the same function on the same frozen revision, so they cannot disagree. A computed cache column may be filled by the server after approval and is always reproducible from inputs. Fixtures pin the acceptance numbers: quality 4 and 5 give 90.0, combined Early 93.3, Middle 80.0, Late 66.7, one permitted N/A gives 80.0 with coverage 1 of 2, absent gives null quality.

**Reopen.** reopen_session requires Owner or Admin and a reason. It clears is_current on the approved revision, which stays immutable, inserts a new pending revision as current, and sets session status to In review without reopening collection. Default analytics include only sessions whose current revision is approved, so a session under revision drops out and is labelled. Reapproval makes the new revision current, so it counts once.

**Concurrency and idempotency.** Every edited row carries an integer version checked by its RPC. submit_assessment looks up the assessor's idempotency key first and returns the existing revision on a repeat, so double taps and retries converge on one submission. Scores are validated as integers 1 to 5 against the frozen template version on the server.

**SSR auth.** Next.js App Router with the Supabase SSR package. Middleware refreshes the cookie session. Server components, route handlers and server actions build a per-request client from the user's cookies and call the RPCs with that identity. Authorization decisions use the server-verified user, not the locally decoded session. Workspace context comes from the route segment, but the layout calls a context RPC on every request to confirm active membership, role, locations and MFA level. A changed workspace id in the URL yields permission denied. Guest users sign in by email OTP and land on their single session. MFA uses Supabase TOTP. Owner and admin writes check assurance level AAL2 in the helper. Enrollment UI ships in M1, hard enforcement is enabled before launch.

**Export authorization.** Exports are generated inside a route handler with the user's own client, so RLS and the context RPC apply. The handler additionally checks role and location scope against the requested session, then records an export audit event. Redacted mode selects assessor-free data at the query layer, so identities never reach the rendering code or document metadata. CSV writer prefixes cells starting with equals, plus, minus, at, tab or carriage return. PDF is rendered server-side with a lightweight library suited to serverless. Every output prints business, filters, timezone, revision and generation time. Exports stream to the client in M1. Stored export jobs are deferred.

**Focused tests.**
- Unit: scoring fixtures above, attendance-off path, all-N/A Not assessed, equal-weight subject-session mean.
- Database, run against the dev project with disposable tenants: two tenants with identical names and copied ids cannot read or write each other through selects, RPCs or invite links. Revoked member fails on an open page save. Last owner cannot be removed. Expired, revoked, wrong-email and reused invites fail. Stale version yields conflict. Repeat idempotency key yields one revision. Approval blocks on unresolved outcome, locks writes, reopen preserves the old revision, reapproval counts once. Tenant key update is rejected. Policies execute without recursion errors.
- End-to-end on Playwright at 390 by 844 in Chromium and WebKit: onboard, invite, session, assess, resolve, approve, reopen, export.
- CI runs on GitHub Actions per pull request and deploys the savour-dev preview.

**Phased scope.**
1. Foundations: migrations, RLS helpers, workspace creation, invites, memberships, SSR auth, audit, isolation and revocation tests.
2. Setup: locations, subjects, categories, template publishing, three seeded starter packs, sessions and rosters.
3. Assessment: assignments, guest grants, mobile form, idempotent submission, save-state UI.
4. Review: outcome resolution, corrections, approval, reopen, scoring package.
5. Reporting: overview with approved-only default, session PDF, results CSV, redaction, export audit.

**M1 omissions, deliberate.** Corrective actions, notifications beyond auth email, billing and quotas, CSV subject import, ownership transfer, attention rules and trends, provisional toggle, stored exports, QR entry page, sample sessions, rate limiting beyond platform defaults, backup restore rehearsal, and MFA hard enforcement. Each has a schema seat or extension point above but no code.

**Requires docs verification before coding.** Supabase SSR cookie helpers and the recommended server-side user verification call. MFA assurance-level claim shape for use in SQL helpers. Email OTP rate limits and whether custom SMTP is needed for invite volume. Supabase CLI migration workflow for the named project. Vercel function size limits for the chosen PDF library.

## Coordinator decisions

Use the modern publishable key, not a legacy anon key. Public RPC wrappers should be SECURITY INVOKER over explicitly authorized private implementations with restricted execution. Idempotency retries must compare payloads; reject reuse with different content. All mutating assessment/attendance/assignment RPCs must share the revision lock used by approval. Keep the entire approved report row immutable: store current revision pointer on the session rather than updating a flag on historical snapshots. Membership, location and assignment revocation must apply to report and export reads immediately. Vercel preview only; no production branch integration. MFA enrollment included; launch enforcement stays a release gate.
